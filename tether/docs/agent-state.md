# Agent state

Tether keeps one agent state per session: `working`, `idle`, `blocked` or `unknown`. It is on the session descriptor (`state`, `stateSource`, `stateAt`, `stateDetail`, `statePrevious`, `stateAgentAt`), on every `session.updated` event, and in `tether sessions diagnostics`. Aico web groups its session list by it, and Tether sends the Nightshift "waiting" notice for a session that stays `blocked`; `st sessions wait --until` uses it to wait for another session.

The state lives in the daemon's memory only. After a Tether restart it is rebuilt from the agents' own files within a poll.

`stateAgentAt` is the agent's own time of its latest state: Claude Code's `statusUpdatedAt`, the time of the Codex turn line, the Pi message's time. A hook report or an Agent Hub poll carries none, so Tether uses its own clock for a change it sees, except on a first sighting after a restart, which keeps the earlier value (0) rather than invent a turn. It only moves forward. A later time while `idle` publishes `session.updated` even though the state did not change: a turn started and ended between two polls. [Lane reports](api-v1.md#lane-reports) use it to say `finished`.

## Inputs

**The agents' own state, polled every 2 s** for each running session. Tether finds the agent in the pane's process tree (re-searched every 15 s, or at once when the agent process exits) and reads:

- Claude Code: `~/.claude/sessions/<pid>.json`. `status` `busy` is working, `waiting` is blocked (`waitingFor` becomes `stateDetail`: `permission prompt`, `input needed`, `dialog open`), `idle` or `shell` is idle. This file is Claude Code's internal state, not a documented interface; the hook below keeps blocked detection working if it changes.
- A Claude Code root with an `entry` ([Roots](api-v1.md#roots)) runs inside whatever its entry leads to, such as a container, so its pid is not one of the pane's and the agent's hooks cannot reach this Tether. Tether finds the entry process in the pane (it carries `TETHER_ENTRY_HOME`, the host path of the agent's home from entries.json) and reads `<home>/.claude/sessions/*.json` instead: one agent runs per home, so the interactive file updated last is the agent's (a parked session's job file stands in for it, as above), and its pid is not checked. The agent runs exactly while the entry process does. Continuity, crash recovery's resume id and its transcript (`<home>/.claude/projects`) read the same home. The host's own `~/.claude` is never read for such a session.
- Codex: the user thread's rollout file, which the Codex process holds open, read incrementally from the end. `task_started` is working, `task_complete` or `turn_aborted` is idle, and an unanswered `request_user_input` call is blocked. Codex records no event while an approval prompt is open, so a tool call that asks for `sandbox_permissions: require_escalated` is blocked until its output appears, when the turn's `turn_context` has an asking `approval_policy` (`on-request`, `untrusted`, `on-failure`) and `approvals_reviewer` is the user. Tether's own sessions run `codex --yolo` and never ask. `exec_approval_request`-style events, if a build ever records them, also count as blocked.
- Pi: its session file, `~/.pi/agent/sessions/--<cwd>--/<time>_<id>.jsonl`, matched by the conversation ID Tether chose at launch (`TETHER_AGENT_SESSION_ID`, `pi --session-id`), read incrementally from the end. Pi appends each message when it completes, so the last `message` entry decides: a user prompt, a tool result, or an assistant reply that runs on (`stopReason` `toolUse`, `pending`, `deferred`, or `length` with tool calls) is working; a reply ending in `stop`, `length`, `error` or `aborted` is idle. A long model call writes nothing, so the state stays working. Pi writes no file before its first prompt (unknown until then), never asks a structured question (Tether runs it with `--approve`), and a `/new` inside Pi moves to a file under another ID, which Tether does not follow. Pi's extension hook delivers context only and reports no state; at a 2 s poll it would add a moving part for little.

- Antigravity (agy): its conversation database, `~/.gemini/antigravity-cli/conversations/<id>.db`, the conversation the pane's `agy` process holds open (`presence/<id>.lock`, or the `.db` itself while agy writes). It is opened read-only for each poll and closed again. Each step has a `status` (agy's `CortexStepStatus`, numbers read from agy 1.4.9's proto descriptor and checked live): a step waiting on the user (9, agy's `ask_question` tool) is blocked (`input needed`); a step pending, running, generating or queued (1, 2, 8, 11) is working; otherwise agy is idle once its newest executor run (`executor_metadata`, written when a run ends, with `last_step_idx`) covers the newest step, whether the run finished, was cancelled (Esc) or failed, and working until then (the model is thinking between steps). A background command agy is still running keeps it working, since agy picks its result up in a new run. `stateAgentAt` is the newest step's `completed_at` (idle) or `created_at`. Before its first prompt agy has no conversation; it is then idle with no time of its own, so it can take a line but never reads as a finished turn. Tether runs agy with `--dangerously-skip-permissions`, so it never waits on a permission prompt. The database is agy's internal state, not a documented interface; after an agy upgrade, check the enum (`CORTEX_STEP_STATUS_*`) still holds. agy can't be a root (no resume adapter), so `st aico create` can't start it; an agy session opened in Aico or with `tether sessions new --tool agy` reports to a coordinator that runs `st aico watch` on it, takes waits and lines, and its asks are answered by a line.
- Agent Hub sessions (tool `agent-hub`, no pane): the session's `turn_state` from Agent Hub, polled every 2 s by Tether. `running` is working, `idle` is idle, and Agent Hub unreachable or the session closed there is unknown. `stateSource` is `agent-hub`; such a session is never blocked.

**Hook reports**, `POST /v1/sessions/:id/agent-event`, from the Claude Code hook in claude-config (`hooks/agent-state.sh`). The hook runs in the pane, knows its session from `AICO_WIDGET_ID`, and posts to the instance socket with a 1 s timeout; it always exits 0.

- `Notification` with `notification_type` `permission_prompt` or `elicitation_dialog`: blocked. `idle_prompt` is not blocked: Claude sends it whenever a finished turn sits idle for a minute, and a finished turn is idle.
- `UserPromptSubmit`: working.

A hook's blocked state holds until the user answers: a `UserPromptSubmit`, or a poll whose status changed after the hook fired and is not waiting. A report carrying a different conversation ID than the session's agent (a nested agent started inside the pane) is ignored.

## Not covered

Screen contents are never read. A question an agent asks in plain text at the end of its turn is `idle`, not `blocked`; only the agents' structured prompts (permission prompts, Claude's AskUserQuestion dialog, Codex's request_user_input) are `blocked`.
