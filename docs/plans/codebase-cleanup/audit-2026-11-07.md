## K. Proxmox host: install an Aico agent on davion-gem?

### What exists today

- Three separate ways Aico talks to the hypervisor, all different:
  1. Unrestricted root SSH from the workstation (alias `davion-gem`; keys `kasadis@summitflow-prod` and `...-admin-2026`, `from=192.168.86.128`). Used by `fleet/src/power.ts` (guest list, `onboot` read through `awk` over `/etc/pve`, `pvesh create ... status/{start,shutdown,reboot}`, `pvesh set ... --onboot`), `tether/src/hub/placement.ts` (`proxmoxArgv`: `pvesh get` of node memory and storage), `aico away` (poweroff), `docs/fleet-link.md` "Powered-off peers" (`proxmoxSsh`).
  2. A forced-command SSH key for CT 190 (`aico-ct190-power`): it runs exactly `pvesh get /cluster/resources --type vm`, whatever command is sent. Plus `aico-push` for alerts. The host firewall lets only 192.168.86.59 reach port 22 (not 8006).
  3. A scoped Proxmox API token, already working: `st vm` (`packages/ops/src/vm.ts`) calls `https://192.168.86.39:8006/api2/json` with `PVEAPIToken`, the token in Aico Logins (`proxmox-vm`), pinned to the PVE root CA, enforced by Proxmox ACLs on `summitflow@pve!automation` (pools `summitflow`, `summitflow-ops`, `summitflow-power`; `VM.PowerMgmt`, `VM.Config.Options`, `Sys.Audit`/`VM.Audit` at `/`). `hosts.json` wake, sleep and status for agent-work and neri-hunters already go through it (`st vm start 200`).
- Already on the host: an Aico Python oneshot timer, `pve-sender` (every 5 min; alerts and watchdog when both Aico machines are silent). No Node on the host (`dpkg`: nodejs not installed); Python 3.13; 54 GB free on root.
- Defects this split causes today (verified, nothing changed): from CT 190 `ssh pve-power "<any command>"` returns the cluster JSON and exit 0, so `guestAction` and `setGuestOnboot` would report success and do nothing (G1); the same forced command makes `readOnboot` return an empty map, so the gem door shows AT BOOT "no" for every guest (G2; the workstation shows yes for 100, 150, 160, 170, 190). A copy of the `proxmox-vm` token sits on CT 190 (`secrets/proxmox-vm`, since 11-05) but port 8006 is firewalled for it, so it is unused.

### Weighing the three options

| | Worker agent on davion-gem | Root SSH (today) | Proxmox API token, scoped role |
|---|---|---|---|
| One channel with the fleet design | Yes, but the fleet channel carries an `exec` frame (argv) to a root process on the hypervisor | No, a second channel | Proxmox's own channel; Aico's fleet link stays Aico-to-Aico |
| Pinned keys and approvals | Pinned Ed25519 allowlist, an owner approval ask per enrollment | Static SSH keys | Token in Logins, scoped, rotatable; creation is a root `pveum` step on gem |
| Needs on a hypervisor | Node 22+ (not installed; ~40 MB), a user or system service, a LAN listener (new host.fw rule, declare), updates and a pin file kept in step with Aico releases, root for `qm`/`pct`/`pvesh` | Nothing | Nothing (API is already running on 8006) |
| Blast radius if Aico misbehaves | Root on the hypervisor and every guest through an exec channel; a bad release reaches the host | Unrestricted root today (the two unrestricted keys) | Only what the role allows: power and `onboot` on named pools, audit everywhere; no shell, no `/etc`, no host poweroff |
| Workstation off | Works (CT 190 dials the host) | CT 190 key is read-only by design, so power does not work | Works from CT 190 with its own token after one firewall rule for port 8006 |
| gem off | Nothing works | Nothing works | Nothing works (same) |
| Update burden | New runtime on a host that is deliberately kept lean (RESCUE.md) | None | None; tokens rotate with Logins |
| Mature-tool comparison | Closest to Proxmox's own cluster agents; Portainer and Rancher run agents inside the workload cluster, not on the hypervisor | Ansible-style, widely used but unscoped | Terraform provider, Proxmox CSI, and Proxmox's own docs use API tokens with privilege separation and per-path ACLs |

### Recommendation: scoped API token, no agent on the host

Do not install a fleet worker on davion-gem. The design's reasons for the fleet link (one pinned channel between Aico machines, approvals, signed updates) do not apply to a service that has its own authenticated API with ACLs, and a worker would add Node, a root listener and an exec channel to the machine whose loss is the worst day. Keep SSH as the manual rescue route (the design's own wording). Keep `pve-sender` as the one small Aico component on the host.

Concrete shape:

1. One Proxmox client in `@aico/fleet` (move `pveRequest`, `routeOp` and `waitTask` from `packages/ops/src/vm.ts`, which already runs `list`, `status`, `start`, `shutdown`, `observe`). Add `getConfig` (onboot read, `GET /nodes/{n}/{qemu|lxc}/{id}/config`) and `setOnboot` (`PUT .../config`), and node status (`GET /nodes/{n}/status`, storage status) for placement.
2. Switch `fleet/src/power.ts` (guest list, power, onboot, `guestPower`) and `hub/placement.ts` (`proxmoxArgv`) to that client. Drop `proxmoxSsh` and the `ssh ... pvesh` argv builders. Keep the "reading failed is never healthy" rule. Replace `AT BOOT` "no" for an unreadable guest with unknown.
3. Two tokens, least privilege:
   - the existing workstation token as is (pools `summitflow-ops`/`summitflow-power`/`summitflow`, `/` audit), renamed from the retired `summitflow@pve` user to an `aico@pve` user with the same ACLs;
   - a new CT 190 token with `Sys.Audit`, `VM.Audit` at `/` and `VM.PowerMgmt` plus `VM.Config.Options` on the pools holding the guests it may start (agent-work, neri-hunters, apps, jobinator, the labs), not CT 190 itself or `/`. Store it in Logins with `machines: ['aico']` and delete the stray copy of the workstation token from CT 190.
4. Firewall: in `/etc/pve/nodes/davion-gem/host.fw` add `IN ACCEPT -source 192.168.86.59 -p tcp -dport 8006` (same style as the port 22 rule) and declare it with `aico declare`. Trust is the pinned PVE CA already on the workstation (`pve-root-ca.pem`); put a copy on CT 190.
5. Remove the replaced access: `aico-ct190-power` key and the `pve-power` alias on CT 190; the unrestricted `nightshift-check@davion-sidarli` key; leave one named manual rescue key for the owner. `aico away` keeps one poweroff path for the host itself (the host cannot shut itself down through its own API token anyway); keep that as the explicit root SSH it is.
6. Tests: unit tests with a fake PVE (the `PveTransport` seam exists); a live check from CT 190 with the workstation link down: list guests, read autostart, start and stop VM 200, place a hunt.

Size: M (one client module, two call-site switches, two tokens, one firewall rule, deleting three access paths). It also removes G1 and G2 and makes the gem door able to power agent-work and neri-hunters, which H14 needs. If the owner later wants Aico to run work on the hypervisor itself, extend the Python `pve-sender` rather than adding Node.
