# M10c-2a Codex review

Reviewed the draft worktree on 2026-11-04 against `briefs/M10c-2a.md`, the old backup/refresh/autosnapshot implementations, the new jobs/routes/pages and the SQLite snapshot helper. Only this report was written. No backup, restore, retention, credential access or live deployment was executed; test and runtime proof remain the builder's work. Files changed during this review, so locations identify the inspected code and each fix still needs its regression test.

## Findings

1. **P1 — Canonicalize physical points before applying holds or deleting.** `packages/ops/src/backup-retention.ts:33` groups by the literal `snapshot_path`. The old `autosnapshot._point_key` rebases different workspace spellings to one managed physical point. An old unpinned view under one spelling can therefore be selected while a pinned or recovery-held view under another spelling is kept; deletion removes the shared physical point anyway. Canonicalize both selection and manifest removal. Regression: two symlink/rebased spellings of one old point, with a pin or recovery copy on just one view, must select neither.

2. **P1 — Independent job locks can overwrite a completed backup receipt.** `packages/ops/src/backup-runtime.ts:94` writes the entire state object last read by a process. The current CLI gives snapshots and the guard independent locks (`backups.ts:317`), so they can finish with a stale state after Drive has saved a new copy. Their final save removes that copy and its clean-run record. Preserve concurrent per-target changes with an atomic state transaction/merge; do not hold the physical snapshot lock throughout a long Drive upload. Regression: interleave two reads, a successful new Drive copy, then a stale guard/sweep completion; both results must remain.

3. **P1 — Snapshot holds describe the live tree before capture, not the frozen tree.** `packages/ops/src/backup-retention.ts:176-208` reads live Git status/HEAD, snapshots later, then records the earlier `unfinished` value and HEAD while cloning the old view's remaining capture metadata. Saved edits made in between can be captured but classified as clean, so their saved-work hold is lost. A project inside a nested subvolume can also be recorded as captured even though a nonrecursive workspace snapshot omits its files. The old `quick_snapshots.capture_snapshot` qualifies nested coverage and reads Git metadata/status from the captured tree before accepting it. Keep an unclassified reservation until those checks pass. Regression: a change injected between live status and capture stays classified as unfinished; an omitted nested project never becomes a completed point.

4. **P1 — CT 150 refresh eventually reoffers the same generation forever.** `packages/ops/src/backup-drive.ts:163` always sends `qualified_previous: null`. The source owner's `scripts/st_extension/backup.py:prepare` explicitly calls `reoffer_current` when a `.previous-*` generation exists without this proof. The old SF `backup_prepare._qualified_previous` supplies the manifest digest, backup id and successful Drive snapshot, allowing the owner's existing qualified retirement policy to progress. Preserve that protocol rather than weakening the extension. Regression: a known successfully uploaded current generation yields the matching qualification; absent/older proof remains null.

5. **P1 — Migration imports upload time as folder data freshness.** `packages/ops/src/backup-runtime.ts:79-89` sets every imported Drive copy's `dataAt` to `job.time`, including off-disk export folders. That reproduces the exact stale-payload/re-upload error the brief forbids until a new backup runs. Derive folder data age from its qualified manifest/files and bound it by capture/upload time, or leave it unknown when unavailable. The existing freshness test exercises `copiedDataTime` but did not exercise this import path. Regression: a successful upload today of an old folder remains old immediately after import.

6. **P1 — Preserve stream payload paths when resolving a registered restore source.** The current `snapshotsFor` mapping at `packages/ops/src/backups.ts:78` replaces every registered snapshot's `paths` with `registered.path`. For Proxmox sources that value is a `proxmox://...` URI, while restic stores `/files-lxc-190.tar`, `/pve-cluster-config.sql`, etc. The page initializes the URI and `restoreFiles` rejects it as nonabsolute. Only constrain ordinary host-folder sources to their registered folder; keep actual payload paths for stream sources. Regression: CT 190 and cluster-config sources expose and restore their stored tar/SQL path.

7. **P2 — The CT 190 page creates a Drive row that no job can ever refresh.** `packages/ops/src/backup-plan.ts:206-217` adds `drive/aico-aico` to CT 190's local state. The workstation writes the real gem Drive result under `pve-ct-190-aico-data` in its own state; CT 190 has no Drive login/job and no propagation of that receipt. Its synthetic row therefore stays “No verified copy yet” even after a good daily copy. Use the actual remote-owned receipt and show its workstation dependency, avoiding a permanently unfillable duplicate row. Regression: a fresh gem Drive copy produces one accurate source/target row on the fleet view.

8. **P2 — A native volume's default restore path is rejected, and native success is labelled verified without a read-back.** `packages/ops/src/backups.ts:119` allows only descendants of `point.target`, rejecting equality. The native volume rows initialize restore to `/`, `/home`, `/srv/workspaces`, etc.; these resolve to the point itself and always fail. Allow the selected root while preserving scratch confinement. The branch then returns success immediately after `cp`/`chown`, while the page says “Restored and verified”; either compare the bytes or use truthful success copy. Regression: a selected native root restores to a new scratch folder and verification has evidence.

9. **P2 — Reusing a root-written rclone copy can stop the second host-volume upload.** `packages/ops/src/backup-runtime.ts:145-146` recopies auth to the same `drive-<pid>.conf` before each root job. A root-run rclone token refresh can replace that file with root ownership; the next unprivileged `copyFileSync` fails with EACCES. This condition is explicitly handled in the old `backup_offsite.prepare_runtime` by unlinking the runtime copy before recreating it. Use a private per-operation/runtime copy with safe replacement and cleanup. Regression: simulate a root-owned refreshed copy between volume jobs; subsequent jobs can still prepare their runtime without modifying the original auth.

10. **P2 — The boot/package consistency window starts too late.** `packages/ops/src/backup-native.ts:137` copies boot files before the package digest is taken at line 150. A package update during boot copying can finish before the digest, then pass the final comparison even though boot and root capture differ. The old adapter hashes package state before `copy-boot`. Move the initial digest before that operation and reject changes through final capture. Regression: changing package status during mocked `copy-boot` prevents a completed recovery receipt.

11. **P2 — Replacing the autosnapshot timer drops baseline creation for newly registered projects.** `captureWorkspace` starts only from existing manifests (`packages/ops/src/backup-retention.ts:164`); a project with no prior manifest is never considered, so no later sweep creates its first view. The old `sweep_periodic` enumerates active scopes, including empty catalogues. Discover active registered scopes without opening protected projects, then create qualified initial views. Regression: an active ordinary project with no manifest receives its first accepted point; protected projects are not inspected.

## Findings corrected during the review

- HTTP Run now originally submitted the workstation's unsuffixed append job on CT 190. The builder changed it to the ops `request` path, which resolves the machine's actual job. Regression proof remains required.
- Weekly verification originally lacked a jobs definition and was rejected by the outer run allowlist. The builder reports adding both; its scheduler/cutover proof remains required.
- The initial all-operation physical snapshot lock was narrowed while reviewing. Finding 2 describes the state-write race that must be resolved with that narrower lock scope.

It does not validate the new key installation, append-only denial behavior, clean backend runs, restored-file comparison, screenshots, uilint, deployed scheduler, or disabled legacy timers. Those are still required by the brief before completion.
