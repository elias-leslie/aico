## Findings

1. **P1 — Portfolio price checking silently omits products after the fourth.** `backend/app/services/household_price_check_service.py:472` replaces the whole-vendor model call with `lookup_vendor_prices_with_firecrawl(adapter, products)`. The previously exceptional fallback still slices `products[:FIRECRAWL_VENDOR_PRODUCT_CAP]` at `_price_firecrawl_lookup.py:116`, with cap 4 at line 37. `execute_run` invokes this once per vendor for the complete selection; selection permits 12 ordinary or 40 shopping-list products. Reproduce with five selected products and successful lookup stubs: only the first four reach `_lookup_product`, so the fifth never gets prices at any vendor. The cap pre-existed; making the fallback the sole path introduces the regression. Process the full admitted selection or explicit batches.

2. **P2 — Jobinator recurring job rows cannot become late.** `backend/app/automation.py:66` publishes each successful scheduled job without `next_run`; `backend/app/aico.py:152` adds it only when passed. Aico `packages/status/src/show.ts:98` explicitly treats rows without `next_run` as never due. Reproduce by completing a scheduled job, keeping the API heartbeat alive, then stopping its Hatchet worker past the next cron: the job stays `ok` indefinitely. Supply each schedule's next due time for success and failure reporting.

3. **P2 — Portfolio publishes degraded price runs as healthy.** Initial `backend/app/workflows/jenny.py:45` (`_reported`) unconditionally sent `state="ok"` for any returned result. `household_price_check_service.py:625` returns `completed_with_errors` when any vendor is blocked/error/partial, including every vendor failing. Reproduce by returning that result from the weekly operation: Status says "Last run completed" and `ok` despite no verified prices. Propagate degraded/failed result states, including the maintenance routine's nested errors. A fix/test was being written during review; not yet independently verified.

4. **P2 — Resolving a notice can leave its question open.** Aico `packages/web-server/src/service-apps.ts:212` resolves only already-recorded `askId`s. `packages/notify/src/notifier.ts:39` starts `noticeAccepted` without awaiting it; `needs-you.ts:109` stores the ask ID only after Tether creates it. Reproduce by holding the Tether ask-create promise, posting a keyed `todo` notice, resolving its key, then releasing creation. Recovery sees `askId=null`; creation subsequently leaves an open question for an ended condition. Coordinate pending creation with resolution or check recovery before retaining the ask. The service route test stubs `notifier.receive`, so it does not exercise this integration.

5. **P2 / scope confirmation — Jobinator discovery loses open employer discovery and can starve later candidates.** `backend/app/agents/company.py:125` now selects only the first ten alphabetical existing `TrackedCompany` rows outside the user's Watchlist. Lines 135–138 restrict the model to those pages; lines 153/162 reject every other source. Previously this agent searched the web and could create a new employer. Reproduce with no registered candidates: the supplied-source set is empty and no new employer can pass. With ten persistently irrelevant/unfetchable first candidates and a matching eleventh, each weekly pass retries the same ten because `profile.discovery_at` advances at line 217 and no cursor/exclusion advances. Restore app-owned discovery and bounded progress, or obtain an explicit decision accepting catalog-only selection.
