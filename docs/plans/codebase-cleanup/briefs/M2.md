# M2 brief (builder: Opus 5.5 high, native subagent)

Goal: milestone M2 in /srv/workspaces/projects/aico. Build the one Status screen exactly as the owner approved it on 2026-11-03: the mockup in `docs/mockups/status/` (index.html, status.js, rows.js, NOTES.md) plus the three recommendations below. The screen, the tray badge data and the phone data all read the same Status rows. A project page is the same list, filtered.

Owner-approved choices (binding):
1. Phone alerts: one alert per batch when a row turns failed, or when a backup or machine row goes late. Warnings and unknowns change only the tray badge and the screen.
2. Rows on a machine turned off on purpose (its machine row says off) still show as unknown, but stay out of the badge count and alerts.
3. Status is a full page. Its sidebar button replaces today's "Health OK" (`packages/web-frontend/components/health/HealthButton.tsx` / `HealthSheet.tsx`) and shows the problem count. On the phone the same button opens it full screen. Needs you stays separate.

Read first:

- `plan.md` "Settled consolidation choices" -> "Status: one screen for the whole fleet";
- `cutlist.md` 1.1 (`web-frontend` imports only ui-kit and contracts types; static export, no server restart), 1.4, and the M2 row in section 4;
- `packages/status/src/show.ts` (the shown state, rollup and filter logic) and `packages/web-server/src/status.ts` (GET /api/status);
- the Aico product standard in your context, and the `design-evidence-review` and `product-copy` skills.

Scope:
1. Status page in web-frontend, matching the mockup:
   - problems first; healthy rows folded into a count that unfolds;
   - filters (state, kind, machine, project, search), sort, and the row actions (run now, detail, log, look into it);
   - the project page;
   - loading, empty, failed (API down), partial and stale states with the mockup's copy;
   - the 390px phone layout, including keyboard-open search.
   Reuse ui-kit tokens and fonts and existing components; no new palette. Ids like `aico` (host, project, CLI) render as ids, so the uilint spelling rule should skip them; adjust `ui-spec.json` narrowly if needed.
2. Wire the actions to what exists today:
   - "look into it" starts a session the way Aico starts one now;
   - "run now" and "log" use the row's `actions` refs;
   - "detail" only where there's real content (backup restore stays a placeholder link until M10c);
   - an action with nothing behind it is hidden, not faked.
3. Badge and summary data: one small endpoint, or a rollup field in GET /api/status, that gives the tray and phone the problem count and top problems with rule 2 applied. M4 points the tray and the phone at it.
4. Phone alert rule 1: if `packages/notify` (M3) has landed by the time you get here, wire the rule through it: transitions seen on upsert, batched, one alert per batch. If M3 hasn't landed, build the transition detection in `status` with a typed hook and leave the notify call to the coordinator; say which.
5. Retire the old Health button and sheet once the Status page replaces them, plus tests that cover only them. Keep anything another screen still uses.
