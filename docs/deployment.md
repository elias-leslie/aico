# Aico deployments

From the workstation checkout, commit and check the source, run `st sessions may-disrupt aico`, then `st service rebuild aico --detach`. Tether (tether@default) is a manual worker, but the deploy restarts it whenever the release changes what it runs (packages/tether, or a package it bundles) or the running daemon's API is older than the release's; the deploy log says why, or that it was left running. Restart it alone with `st service rebuild aico --worker tether@default --detach`. Wait for each printed job result and verify health.

## CT 190, the standalone full peer

CT 190 has no Git checkout and too little memory to build. It runs the same commit-named release the workstation built and accepted. It follows the workstation by itself: the aico-jobs job `peer-release` (every 15 minutes on the workstation, `scripts/peer-release.sh aico-gem aico`) sends the release named in `~/.local/lib/aico/releases/.accepted` (the deployer writes it once a release passes acceptance and goes live) whenever CT 190 runs another commit, declaring the change to Nightshift first, then pushes the workstation's signed Tether over the fleet link (`tether fleet push-update`; installed only when it differs and is newer). A release whose deploy built no Tether keeps CT 190's installed Tether (`install.sh --keep-tether`). It waits while a workstation deploy holds the releases lock. Its Status row says what it sent. To send one now, or a chosen commit, run `st sessions may-disrupt aico`, then from the workstation checkout:

```
scripts/deploy-remote.sh aico-gem            # the commit the workstation runs now
scripts/deploy-remote.sh aico-gem --sha FULL_COMMIT
```

It copies the workstation release (the commit's source plus its `node_modules`, built bundles and `packages/web-frontend/out`; no build caches, runtime state, `.env` or auth files) into a **new** `~/.local/lib/aico/releases/FULL_COMMIT` on the CT, unchanged files hard-linked to its current release. It compares every file's checksum against the workstation copy, then runs that release's `AICO_INSTALL_SOURCE_SHA=FULL_COMMIT bash scripts/install.sh --prebuilt --start` and waits for web health. `--prebuilt` checks the required bundles, static page and dependencies before installing files and runs no dependency install or build. The CT keeps its configuration and data. `--dry-run` shows the copy and changes nothing.

### The owner's context on the standby

The workstation writes the memories, prompts, roles and launch policy (context.db); the CT only reads them. The `context-sync` job (workstation, every 5 minutes; `aico context-sync run`) hashes those tables, asks the CT for its hash over the fleet link (`tether fleet exec`, the channel the repo copies use) and, when they differ, sends a consistent snapshot of just those tables (`VACUUM INTO`, then the delivery log emptied). The CT replaces its copy of the tables in one transaction and records the sender and hash in `~/.local/state/aico/context-replica.json`, which also marks that context as a copy. The CT's delivery log, context-cost rows and everything else in its context.db stay its own. Memories, prompts, roles and the launch policy are not edited on the CT: a snapshot of another schema version is refused (the next peer-release run brings the CT to the same release), and `aico context-sync` refuses to run on a machine whose context is a copy.

If a session on the CT does save a memory or edit a prompt, it is not merged back. The next sync keeps the CT's whole file as `context-replica-before-STAMP.db` beside context.db (the last five), says so in the job's last output (Routines), and then replaces the tables, so nothing is lost silently. Re-save what matters on the workstation. During a workstation outage the CT works from the last copy; a memory saved there waits in that kept file for the owner. Check with `ssh aico-gem aico memory list` against the workstation's.

### Working checkouts and jobs on the standby

The workstation's `aico wip run` (job `wip-mirror-davion-sidarli`) also keeps a working checkout of each copied repo on the CT, at the same path as on the workstation (for example `/srv/workspaces/projects/aico`), on the branch the workstation has checked out, and lists it in the CT's projects (`aico projects register`), so a session on the CT starts in a project the same way when the workstation is down. Uncommitted work stays in the mirror (`aico wip restore`). The checkout is only ever fast-forwarded: one on another branch, with its own changes or commits, or a folder that is not a Git checkout is left as it is and named in its Standby checkout Status row. A clean checkout with nothing of its own follows the workstation's branch when that changes. The checkout's remote is `wip-<machine>`, pointing at the mirror. Which machines' repos get checkouts is `standby.from` in packages/ops/data/wip-mirror.json.

Jobs with `lease_host: aico` and both machines as `workers` (note-reminders, morning-digest, and routines registered with `--hosts either`) run on the CT when the workstation misses them by one lease period. The CT holds their lease. A job that names the workstation in `fallback` (note-reminders and morning-digest in packages/jobs/data/jobs.json) still runs on the workstation while the CT gives no answer at all (a connection error, not a refusal), on a lease in the workstation's own jobs.db. The workstation keeps its own copy of the CT's due time and pause for this, and does not stand in for a run the CT held a lease on when it was last reached until that lease runs out. A run that went through the CT's lease but whose result the CT could not take is kept on the workstation the same way. When the CT is back, the workstation hands that run over (`report`). Before the CT runs a slot it missed, it asks the fallback workers whether one already ran it (`standin`), and waits up to one lease period after a restart for that answer. So a run is not repeated when either machine comes back first. The CT waits while the workstation is still running a slot in its place, and asks for at most one scheduler tick (5 s) per due slot. A drop of the link shorter than one lease period is covered: the CT asks before it runs. A longer split (both up, the link down) runs the slot on both machines. Without a third machine to break the tie, that is the cost of standing in. Routines and jobs without `fallback` wait for the CT, as before. A digest sent from the CT describes the CT's sessions and Status, with spend shown as unavailable (it has no usage.db). The CT's Status row for a job the workstation runs follows the result the workstation reports to the CT's lease (the CT's scheduler rewrites the row whenever the job's state changes there), and a removed routine's row is taken down by the scheduler that wrote it.

### Browser on CT 190

`scripts/peer-release.sh` also runs `scripts/peer-tools.sh aico-gem`, which puts the workstation's `aico-hook` on the CT (`st sessions inbox` and the edit guard need it; the CT has no Go) and the browser runtime. `st browser` runs the workstation's accepted browser-automation release: the script copies that release without its `.venv`, builds the CT's own with `uv sync --frozen` (uv is copied over once) and installs the pinned agent-browser with `npm ci`. Sessions run on the browser VM (VM 100), not on the CT, so the CT needs no Chrome. What the scripts do not do is host configuration, set once:

- `st vm ip 100` works from the CT: the Proxmox role `AicoAudit` (token `aico@pve!ct190`) holds `VM.GuestAgent.Audit`.
- The CT reaches the VM over SSH: its own key `~/.ssh/id_ed25519_browser_vm`, named for the VM's address in the CT's `~/.ssh/config`, and its public half in the VM user's `authorized_keys`.
- The VM accepts the CT's CDP connections: `/etc/pve/firewall/100.fw` allows tcp 9300:9339 from 192.168.86.59 (port 9222 stays workstation only), and the VM's `~/.config/st-browser/chrome.env` has `ST_BROWSER_CDP_ALLOW=192.168.86.0/24` (socat takes one range; the VM firewall is the real allowlist).
- A login the CT's routines use (for example the Focus parent portal, `st browser login focus-pcsb`) needs machine `aico` allowed: on Aico's Logins page or by any agent with `aico logins allow focus-pcsb --machine aico` (logged in the login's activity; docs/adr/0003-logins-agent-self-service.md).

Tether alone also reaches peers on its own: a workstation holding the update signing key signs each Tether release it installs, and its hub sends that signed release to a pinned peer whose Tether API is older when their link comes up.

Afterward verify web health, Tether health, active unit paths, a synthetic Logins entry reaching both peers and its removal reaching both, the CT's own append-only backup job, and its heartbeat Status row. Read metadata only; never reveal the entry's value.

Rollback uses the retained prior release's installer and bundles. Restore its unit and launcher targets, retaining the newer data; no database restore or backup deletion is part of a code rollback.
